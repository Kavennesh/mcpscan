# MCP-008 — Tool read outside its declared scope

**Severity:** critical · **Defined in:** `src/mcpscan/probes.py`, driven by `src/mcpscan/prober.py`

## What it detects

A declared tool that returns the contents of a file it was never meant to reach.

Before the scan starts, `canary.py` writes a decoy tree to a host temp directory
and bind-mounts it read-only at `/home/canary` inside the container:

```
/home/canary/.ssh/id_rsa          mcpscan-canary-<32 hex>
/home/canary/.aws/credentials     mcpscan-canary-<32 hex>
/home/canary/.env                 mcpscan-canary-<32 hex>
/home/canary/.config/gh/hosts.yml mcpscan-canary-<32 hex>
```

Each holds a distinct token, generated seconds earlier, in a body shaped like the
real thing so a naive reader takes the bait. The probe then calls every declared
tool with traversal payloads and searches the response for a token.

## Why the confidence is HIGH without a benign corpus

Every pattern rule in this project is gated by ~50 realistic benign descriptions,
because pattern matching is a judgement call. This rule is not.

The token is a 32-hex string that exists in exactly one file on the system and was
generated after the scan began. A response containing it can only have come from
reading that file. There is no threshold to tune, no phrasing to argue about, and
nothing for a corpus to calibrate — which is why `test_canary.py` spends its
effort proving the *absence* side instead: near-misses like the bare prefix, a
prefix with a plausible wrong suffix, and a token from a different scan all stay
silent.

## Payloads and argument selection

Arguments come from the tool's own `inputSchema`: every `string`-typed property is
a candidate, `required` ones first. A tool with **no** string property is not
probed, and the scan says so in a coverage note rather than inventing an argument
name — a call the server rejects would produce an absence of evidence that reads
exactly like safety.

```
/home/canary/.ssh/id_rsa
../../../../home/canary/.ssh/id_rsa
~/.ssh/id_rsa
....//....//....//....//home/canary/.ssh/id_rsa
%2e%2e%2f…                                   (URL-encoded)
..\..\..\..\home\canary\.ssh\id_rsa          (backslash)
file:///home/canary/.ssh/id_rsa
/proc/self/environ
```

The default budget tries the first four per tool; `--deep` tries all of them. One
proof per tool is enough — further payloads only repeat the same finding.

## What does not fire, and why that matters

`tests/fixtures/servers/server_escapes_scope.py guarded` is the same
file-reading tool with the check a real server should have:

```python
resolved = os.path.realpath(os.path.expanduser(path))
if not resolved.startswith(ALLOWED_ROOT + os.sep):
    raise ValueError(...)
```

It produces nothing. Without that fixture this rule would be indistinguishable
from "warn on any tool that reads files", which is not a finding — it is a
description of what filesystem servers do.

`server_clean.py`'s `read_file` also produces nothing: it returns a canned string
rather than opening the path.

## Remediation

Resolve and constrain every caller-supplied path before opening it. Expand `~`,
resolve symlinks with `realpath`, and check the *result* is still inside the
directory the tool is documented to serve — checking the input string is not
enough, because `....//` and `%2e%2e%2f` both survive a naive prefix test.

The model chooses these arguments, and it is reading tool descriptions written by
the same server. Treat them as untrusted input from an attacker who also wrote
your documentation.

## Reading a finding

`metadata.argument` and `metadata.payload` reproduce the exact call; `evidence` is
`argument=payload`. `metadata.canary` names which decoy came back, so a tool that
reaches `.aws/credentials` but not `.ssh/id_rsa` is distinguishable.

The token itself is redacted from all output — printing it would teach a reader to
grep for a string that will never appear again.
