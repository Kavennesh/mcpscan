# MCP-003 — Tool parameter reaches a dangerous sink unsanitised

**Severity:** critical · **Defined in:** `src/mcpscan/taint.py`

This rule is implemented in code rather than YAML. Taint analysis is not pattern
matching: a regex over source finds the string `subprocess.run(cmd)` and cannot
tell you whether `cmd` came from the caller, from a config file, or from a
literal three lines up — and that difference *is* the finding. Only a parse
knows, so forcing it into the rule schema would corrupt the schema for the rules
that genuinely fit.

## What it detects

A parameter of a tool function reaching a dangerous call without being
constrained on the way.

**Sources.** Every parameter of a tool function, identified by decorator
(`@mcp.tool()`, `@server.tool()`, `@app.call_tool()`) and by name-match against a
live server's tool listing when one is available. `self` and `cls` excluded.

**Sinks.**

| family | severity |
| --- | --- |
| `subprocess.*` / `os.system` / `os.popen` / `os.exec*` with `shell=True` | critical |
| the same, list-form | high |
| `eval`, `exec`, `compile`, `__import__` | critical |
| `open` and friends on a **non-constant** path | medium |

**Propagation.** Assignment, augmented assignment, f-strings, `+`, `%`,
`.format()`, `.join()`, `str()`, subscript and attribute access, tuple unpacking,
loop variables.

## Why it matters

The model chooses these arguments, and the model is reading tool descriptions
written by the same server. A server that both describes a tool and executes its
arguments through a shell controls both ends of that loop.

## What does not fire, and why that matters

Taint is killed by the shapes a careful server actually uses:

```python
subprocess.check_output(f"grep {shlex.quote(pattern)} log", shell=True)   # quoted
path = ALLOWED_REPORTS.get(name)                                          # allowlist
open("/etc/mcpscan-demo/config.toml")                                     # constant path
subprocess.check_output(["df", "-h", "/data"])                            # constant argv
safe = "/data/" + os.path.basename(path)                                  # basename
```

The allowlist case is the important one: `ALLOWED.get(name)` and `ALLOWED[name]`
are the same operation, and in both the parameter *selects* a value rather than
becoming one. A rule that missed this would report every correctly-written tool,
which is the fastest way to get a scanner switched off.

## Known limitations

Stated here rather than discovered from a false negative:

- **Intraprocedural.** A parameter handed to a helper that calls the sink is not
  followed. This is the largest gap and the obvious next increment.
- **Path-insensitive.** A guard like `if x not in ALLOWED: raise` does not clear
  taint, so a correctly validated parameter can still be reported. Deliberately
  the safe direction, and why the sanitiser list matters.
- **No alias analysis** beyond conservative subscript and attribute propagation.

## Remediation

Do not pass a tool parameter into a shell, an interpreter, or a filesystem path
without constraining it first. Prefer an allowlist lookup over interpolation;
where a shell is unavoidable, quote with `shlex.quote`. Prefer list-form
`subprocess` over `shell=True` — it removes the shell from the picture entirely.

## Reading a finding

The finding is two-place. `location` is the sink — where the bug is.
`related[0]` is the tool function — why it is one. `metadata` names the `sink`,
the `parameter`, the `tool`, and whether `shell` was true.
