# MCP-001 — Invisible or deceptive Unicode in tool metadata

**Severity:** high · **Defined in:** `src/mcpscan/rules/MCP-001.yaml`

## What it detects

Characters in a server's advertised metadata that a reviewer cannot see, or that
change what a reviewer sees relative to what the model receives:

| pattern | characters | confidence |
| --- | --- | --- |
| `bidi-control` | U+202A–202E embeddings and overrides, U+2066–2069 isolates | high |
| `tag-characters` | U+E0000–E007F | high |
| `format-character` | any other `\p{Cf}`, subject to the context check below | medium |
| `private-use` | `\p{Co}` | medium |

The scan covers every string a model can read, not just tool descriptions:
titles, names, annotation titles, resource and prompt fields, and descriptions
nested inside `inputSchema` — the last because being one level down is exactly
what makes a schema description a good hiding place.

## Why it matters

A tool description is reviewed by a human and consumed by a model, and these
characters break the assumption that both see the same thing.

- **Tag characters** are invisible in every renderer and carry a full ASCII
  alphabet. An entire instruction can be spelled out in them, sitting inside a
  description that reads as one harmless sentence.
- **Bidi overrides** reorder displayed text. What a reviewer reads is not the
  byte sequence the model is given.
- **Zero-width characters** can split a word so that a reviewer's search for a
  suspicious phrase does not find it.

## What does not fire, and why that matters

Several format characters are load-bearing in ordinary text, and a rule that
flagged them could not be pointed at a real server. Each candidate is asked
whether it is doing the job it exists for:

| character | suppressed when |
| --- | --- |
| ZWJ `U+200D` | both neighbours are `Extended_Pictographic` — an emoji sequence |
| ZWJ, ZWNJ `U+200C` | an adjacent character is Arabic, Hebrew or an Indic script |
| LRM/RLM/ALM | the field contains strong right-to-left text |
| BOM `U+FEFF` | at position zero, where it is a byte-order mark |

```
Search 👨‍👩‍👧 family records.        -> nothing.  ZWJ joins two pictographs.
Returns the 🏳️‍🌈 emoji.             -> nothing.  The check walks past U+FE0F.
ملف‌ها را فهرست کند.                  -> nothing.  Persian ZWNJ is orthographic.
מחזיר את תוכן הקובץ ‏README.md       -> nothing.  RLM with RTL text present.
Reads a file.‍PAYLOAD                -> MEDIUM.   ZWJ between two ASCII chars.
```

The check is narrow in both directions. "That is how emoji work" is only an
excuse where there are emoji, so the same ZWJ that is silent inside a family
emoji is reported between two ASCII characters. And the RTL search deliberately
excludes the directional marks themselves — they carry a strong bidi class, so a
naive search would let a lone smuggled RLM justify its own presence.

## Remediation

Remove the characters, or replace them with their visible equivalents. Text a
reviewer cannot see is text they cannot review, and every one of these reaches
the model exactly as the visible characters around it do.

If a description genuinely needs non-Latin text, it will pass: the suppressions
above exist precisely so that Persian, Hebrew, Indic and emoji content is not
penalised.

## Reading a finding

`metadata.characters` lists every reported character with its codepoint, Unicode
name, character offset and **byte offset**. The two offsets differ whenever
multibyte text precedes the payload, and the byte offset is the one to grep for.

A run of the same category is reported once, not once per character: a
200-character tag payload is one problem. Where the broad `\p{Cf}` sweep overlaps
a specific pattern, the specific one wins — a bidi override is reported once as
what it is, not twice.
