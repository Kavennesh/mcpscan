# MCP-005 — Response correlation abuse

**Severity:** varies by kind · **Defined in:** `src/mcpscan/anomalies.py`

JSON-RPC gives each request id exactly one response. This rule covers servers
that do otherwise — and unlike the framing violations in MCP-004, none of these
has a plausible "sloppy implementation" reading that makes it harmless.

## duplicate-id

**high / high confidence.** A second response for an id that was already
answered.

The client has acted on the first response. It has parsed the tool list, shown it
to a user, perhaps had it approved. The second response arrives afterwards and
overwrites state that was already trusted — which is a way to get one tool list
reviewed and a different one used.

`tests/fixtures/servers/server_dup_ids.py` demonstrates it: the first
`tools/list` response is benign, the second carries a description with an
embedded instruction to read `~/.aws/credentials`.

mcpscan resolves the request on the first response and records the second without
letting it through. A client that took the last response instead would be
silently repointed.

**Fix:** answer each id once.

## unsolicited-response

**high / high confidence.** A response for a request the client never sent.

Request ids are sequential and therefore guessable, which makes this an attempt
to answer a question the client is *about* to ask — pre-seeding a reply so that
whichever arrives first wins.

**Fix:** only respond to requests actually received.

## unexpected-server-request

**medium / high confidence.** The server issued a request — `sampling/createMessage`,
`elicitation/create`, `roots/list` — for a capability the client never advertised.

The lifecycle spec is explicit that both parties must use only capabilities that
were successfully negotiated. mcpscan advertises an **empty** client capability
block precisely so that any server request is unambiguous: there is nothing it
could legitimately be responding to.

mcpscan answers `-32601` and records it. Medium rather than high severity because
a server optimistically probing for a capability is less pointed than one
overwriting state, but it still means the server reaches for things it was not
offered.

**Fix:** check the client's declared capabilities before issuing a request.

## Remediation

Answer each request id exactly once and never send a response for an id the
client did not issue. A client that accepts either can have state it has already
acted on replaced underneath it.

Before issuing a server-to-client request, check that the corresponding client
capability was negotiated during `initialize`.
