# MCP-006 — Protocol conformance and capability mismatch

**Severity:** varies by kind · **Defined in:** `src/mcpscan/anomalies.py`

Where a server's declared shape and its actual behaviour disagree.

## undeclared-capability

**high / high confidence.** The server answered `tools/list` (or the resource or
prompt equivalent) while declaring no such capability during `initialize`.

This is the highest-value kind in the rule, because of what an *ordinary* client
does with it: it reads the empty capability block, skips the request entirely,
and reports a server with no tools. The tools are right there and callable.

That gap is why mcpscan probes every list method regardless of what was
declared. A capability that is not declared is a capability that nothing
reviewing the declaration will ever see — a way to keep a tool out of an audit
while leaving it available to the model.

`tests/fixtures/servers/server_undeclared.py` demonstrates it: empty
capabilities, one tool named `exfiltrate`, served on request.

**Fix:** declare every capability the server actually serves.

## cursor-loop

**medium / high confidence.** Pagination that does not terminate — either the
same `nextCursor` returned forever, or a fresh one every time.

Cursors are opaque by specification: clients must not parse, modify or persist
them, so there is nothing to validate and no way to tell progress from a loop by
inspection. A client that pages until `nextCursor` is absent pages until it dies.

mcpscan's only defences are a seen-cursor set and a 50-page cap. When the cap is
what stopped it, a separate `page_cap` coverage note records that the listing is
**incomplete** — see below.

**Fix:** return no `nextCursor` on the last page.

## version-downgrade

**low / high confidence.** The server answered `initialize` with an older
protocol revision than was offered.

The spec permits the counter-offer, so this is low severity — an old server is a
normal thing to meet. It is reported rather than accepted silently because older
revisions carry weaker rules: 2025-03-26 still permitted JSON-RPC batching, and
revisions before 2025-06-18 predate the guidance making tool annotations
explicitly untrusted. A server that talks its client down a revision has chosen
the ground.

**Fix:** support the latest revision you can.

## Related coverage notes

Four anomaly kinds are deliberately **not** findings under any rule, because they
describe what the scan could not do rather than what the target did wrong. They
appear in `coverage.notes` in the JSON report:

| kind | meaning |
| --- | --- |
| `page_cap` | The listing was truncated at the cap. Results are incomplete. |
| `request_timeout` | A request went unanswered; that surface was not examined. |
| `transport_closed` | The target's stdout closed early; the scan did not finish. |
| `unsupported_version` | No shared protocol revision; the scan never started. |

Reporting these as findings would fill a report with the scanner talking about
itself. Suppressing them entirely would be worse: a truncated listing that
reports "no findings" is a scan that examined part of a server and said nothing
about the rest.

## Remediation

Declare every capability the server actually serves, terminate pagination, and
negotiate the latest protocol revision supported. A surface that is not declared
is a surface nothing reviews.
