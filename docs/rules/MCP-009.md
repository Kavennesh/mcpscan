# MCP-009 — Environment secret disclosed in a server response

**Severity:** high, or critical when the variable was never declared ·
**Defined in:** `src/mcpscan/probes.py`, driven by `src/mcpscan/prober.py`

## What it detects

A server that puts the value of an environment variable into something it sends
back.

`Target.env_keys` carries variable *names* only — CLAUDE.md's third constraint,
and `test_config_import_never_captures_secret_values` proves a real value cannot
survive a config import. At launch, `canary.py` generates a fresh token for each
name and passes those as the container's environment. Anything that comes back
containing one of them was read out of the environment we supplied.

Every surface a server can speak through is searched, not just tool output:

- tool `content` text and `structuredContent`
- `isError: true` payloads and protocol errors
- resource contents
- the `instructions` field from the handshake

## <a id="undeclared"></a>Declared versus undeclared

mcpscan injects canaries for the variables the target declared **and** for a set
of well-known credential names it did not: `GITHUB_TOKEN`,
`AWS_SECRET_ACCESS_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `SLACK_TOKEN`.

These are different acts and are ranked differently:

| what happened | severity |
| --- | --- |
| echoed a variable the target declared | high |
| echoed a variable it never declared | **critical** |

Mishandling a credential you asked for is careless. Reading one you never
mentioned means the server went looking — it had no reason to expect that
variable to exist, and it read it anyway.

## Why the confidence is HIGH without a benign corpus

The same property MCP-008 rests on: the token is generated after the scan begins
and injected into exactly one place. A response containing it cannot have arrived
any other way. See `docs/rules/MCP-008.md` for the longer argument and
`tests/test_canary.py` for the near-miss cases that must stay silent.

## Why `isError` counts

A tool result with `isError: true` is a *successful* protocol exchange whose
payload happens to describe a failure — and that payload reaches the model's
context, the transcript, and whatever logs the transcript. A server that fails
while quoting the token it just read has still disclosed it.

`tests/fixtures/servers/server_leaks_env.py error` exists to keep that path
tested; a probe that only searched successful responses would miss it entirely.

## What does not fire

`server_clean.py` returns fixed strings and produces nothing, as does any server
that reads its configuration without echoing it. Reading a variable is not the
finding — putting it in a response is.

## Remediation

Never echo environment variables into tool output, structured content or error
messages. Log them nowhere, and redact them from exception text before it becomes
a tool result: a stack trace that interpolates a connection string is the most
common way this happens.

If a tool needs to report *which* account or key is in use, report an identifier —
an account name, a key fingerprint, the last four characters — not the secret.

## Reading a finding

`metadata.variable` names the variable and `metadata.declared` says whether the
target asked for it. `metadata.surface` says where it came back — a tool name, a
resource URI, or the handshake instructions.

`evidence` is the surrounding response text with the token replaced by
`<env canary NAME>`, so the finding shows the shape of the leak without printing
a value that will never recur.
